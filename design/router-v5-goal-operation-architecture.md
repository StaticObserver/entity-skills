# Entity Router v5: Goal → Operation → Evidence

Date: 2026-07-19
Status: implemented (run Goal v1)
Baseline: [current architecture notes](current-entity-router-architecture-2026-07-19.md)

## Goal

Ordinary users and the main Agent only describe goals, confirm science/resource/deletion
decisions, and read results. Case UID, Action, Locator, binding, revision, lease,
owner/domain, and recovery steps are all derived by the program.

The public model is:

```text
Project → Goal → Operation → Evidence
```

The public commands are:

```text
entityctl plan   --project-root <path> --goal <goal.json> --output <plan.json>
entityctl apply  --plan <plan.json>
entityctl status --project-root <path> [--live]
```

`doctor`, `install`, and the one-time `migrate` belong to the management plane and do
not enter the normal simulation flow.

## Core Objects

### Project / Case

A Case stores only the persistent facts that span Operations: project binding, source
authority, Site, current source/build/run/data/analysis identities, and evidence
references. Readiness is a derived view of these facts.

### GoalSpec

A GoalSpec contains only user semantics. The first version supports `run`, later
extended with `build`, `data`, `analysis`, and `purge`, all under the same outer
contract. All IDs, paths, hashes, owners, and validation conditions are generated by the
Planner.

### Plan / Operation

A Plan is the immutable execution plan that a GoalSpec resolves to on an exact
Case/Site/source revision. The first time Apply receives a Plan it creates an Operation;
re-Applying the same Plan must resume or return the cached result, and must never repeat
side effects that cannot be safely replayed.

### Step

A Step is the internal journal unit of an Operation, not a public Action. Each Step uses
a fixed set of states:

```text
pending → intent_written → effect_observed → verified → committed
```

Failure states are `needs_decision`, `blocked`, or `anomaly`. A repeated Apply recovers
from the controller journal and the execution-site receipt.

### Evidence

The Controller stores only exact Locators, fingerprints, effect identities, and
verification times. Long logs, builds, runs, raw data, and analysis artifacts remain on
the owner site.

## Controller Store

`~/.entity-router/router.db` is the only structured state of the v5 controller. SQLite
transactions commit the Operation step, identity/current pointer, event, and final
result together, replacing hand-rolled transactions across multiple JSON files.

One-time migration import of the old `registry.json`, `project-bindings.json`, site
JSON, and Case v3 is not yet implemented: the store schema currently has only v1, and
`entityctl migrate` fails outright on any non-current schema ("no migration path ...
implemented yet"). Once migration is implemented, the original files are kept as
read-only evidence; there is no dual-writing between the two state sets.

The database stores only small JSON payloads and evidence references, not raw data or
full logs. JSON export is provided for auditing and debugging.

## Planner Contract

The Planner must:

1. discover or create a Case from cwd/project root;
2. validate the GoalSpec, returning `needs_decision` when genuine science/resource
   decisions are missing;
3. pin the source revision, Site, and input/build identity;
4. complete site/resource preflight before creating the run identity and remote run
   root;
5. derive all IDs, Locators, bindings, acceptance checks, and StepSpecs;
6. emit a canonical plan hash; the same facts produce the same plan.

## Apply Contract

Apply must:

1. validate the plan hash against the current Project/Case/source/Site;
2. acquire an expiring Operation claim inside the controller, without exposing a lease
   to the user;
3. execute allowlisted Steps in order;
4. record an intent before each external side effect;
5. recover already-occurred side effects from execution-site receipts;
6. have the Controller re-probe outputs;
7. commit the Step, identity, event, and Operation state in one SQLite transaction;
8. return to the main Agent only on `needs_decision`, a new anomaly, or terminal state.

There is no separate `recover` command; recovery is Applying the same Plan again.

## Executor Contract

Local and SSH use the same immutable StepSpec and the same content-addressed executor
bundle. The SSH transport only:

1. installs/reuses the exact bundle;
2. stages the request and necessary payload;
3. invokes the allowlisted adapter;
4. returns the result/receipt.

The Executor does not accept `command`, `shell`, `script_text`, or `pre_command`.
Cluster modules, partitions, and policies live in site-local configuration/adapters, not
in the generic GoalSpec or the core skill.

## Owner Skill Contract

`entity-pgen` and science analysis follow "explore freely, converge strictly": the
Router provides the goal, input identities, workspace envelope, protected paths, and
acceptance conditions; the owner skill freely chooses the concrete method; the Controller
finally re-probes the changed/output Locators and commits the evidence.

## Invariants

- The project Git, controller, execution site, and skill bundle each have a single
  authority;
- each Case has exactly one source authority;
- the source → build → run → data → analysis identity chain must not break;
- Site and path together form resource identity;
- external side effects must not be blindly replayed;
- Worker narratives cannot advance state;
- raw data deletion requires an exact manifest and explicit authorization;
- normal queries do not write state and do not access remotes by default.

## Migration Strategy

1. Implement the v5 store, Planner, Apply, and Status alongside the existing code;
2. import v3 registry/site/project/Case, then stop dual-writing to imported objects;
3. complete local and SSH run prepare/launch/status with the unified executor;
4. move the old state/flow CLI to the `legacy`/developer surface;
5. rewrite `SKILL.md`, keeping only the v5 entry points and invariants in the normal
   context.

## Completion Gate

- A normal run needs only one Plan and one Apply;
- GoalSpec contains no ID, hash, Locator, binding, owner/domain, or lease;
- replaying the same Plan does not repeat `sbatch`;
- the controller can recover via Apply after a crash at any Step boundary;
- Local and SSH use the same StepSpec;
- the user is asked only about science, resource commitments, deletion, or genuine
  ambiguity;
- `status` reads only the controller by default; `--live` makes at most three bounded
  scheduler queries;
- one-time v3 Case import is not yet implemented (migration route above); once
  implemented, import does not dual-write;
- the full Router test suite, Python 3.6 grammar, real SSH canary, and
  `git diff --check` all pass.
