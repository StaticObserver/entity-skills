## Skill level: three core findings

### 1. Zero use of the router main path (most important)

All 18 entityctl calls were `doctor`, `site list/discover/add`, `plan --help`, and
`submission create` — **`plan`/`apply` were never executed even once**. The `cases` and
`operations` tables in router.db are empty. At wrap-up, `entityctl submission create`
was rejected with "no Case covers project path" (exit 2), and the agent hand-wrote
submission.json instead.

Credit where due: the agent correctly registered the m87 site profile via
`site discover` + `site add` (transport=ssh, scheduler=none, roots complete) — the
discover/register path works. The break is at the step entering the Goal → Operation
chain: on a Slurm-less site the agent has no motivation to go through plan/apply —
router 0.5.0's run Goal is built around Slurm submission, and with scheduler=none there
is no mappable action path, so the skill degenerates from a "control plane" into a
"site registrar".

### 2. env-build skill invoked 0 times; the build went in raw

activities statistics: env_build 0, raw build 15. The agent directly iterated
`ssh m87 'cmake ...'` over and over, repeatedly `rm -rf entity-build` to rebuild along
the way, and got stuck troubleshooting LD_LIBRARY_PATH / cudart linking problems
(readelf/ldd debugging). The build eventually succeeded, but the entire convergence cost
was paid in raw commands.

### 3. "Run exactly once" was not achieved

The transcript contains a dozen-plus trial TOMLs (test_short, test_warm, prod, prod2,
dt, lc, bp_test, proper……), including segfault debugging (`ulimit -c unlimited`).
Intermediate artifacts such as `proper/` and `neutral_streaming.ckpt` remain in the run
root. The final run itself was correct, but the process was "trial-and-error locally a
dozen times until it works", not a controlled single execution — without a scheduler /
control-plane constraint, this task clause is effectively unenforceable.

### 4. nt2py is the only heavily used skill

skill call distribution: nt2py 106, router 18 (see above — really registration), pgen 2,
env_build 0. `skill_call_share = 0.894` looks excellent on the surface, **but it is
entirely propped up by nt2py**; build/run — the two stages most in need of skill
intervention — were entirely bare. Reporting a single overall adoption ratio masks this
— recommend reporting it broken down by stage (build/run/analysis).

## Attribution and follow-up candidates (recorded, no revisions for now)

This S-group round succeeded at the task level, but for skill attribution it is
counter-evidence: the router's Goal/Operation chain has no entry path on a
scheduler=none site. Candidate improvement directions:

1. **Router support for a scheduler=none run Goal** (direct runner execution:
   foreground/nohup run + PID/log receipts), giving scheduler-less sites a plan/apply
   action path too;
2. **env-build coverage of the "bare build on a personal workstation" path** (dependency
   convergence with no module system and no pre-staged source-cache) — this round's 15
   raw build iterations are exactly its target scenario;
3. **Adoption reporting broken down by stage**, so high-frequency nt2py calls do not
   dilute the raw-command signal in build/run;
4. task.md's "run exactly once" clause lacks an enforcement mechanism on scheduler-less
   sites; either rewrite it as a verifiable constraint like "production runs and trial
   runs must be distinguishable (naming/directory isolation)".
