## 技能层面：三个核心发现

### 1. Router 主链路零使用（最重要）

18 次 entityctl 调用全部是 `doctor`、`site list/discover/add`、`plan --help`、
`submission create`——**`plan`/`apply` 一次都没有执行**。router.db 里
`cases`、`operations` 表为空。收尾时 `entityctl submission create` 因
"no Case covers project path" 被拒绝（exit 2），agent 改为手写
submission.json。

值得肯定的部分：agent 通过 `site discover` + `site add` 正确注册了 m87
site profile（transport=ssh、scheduler=none、roots 完整），发现/注册路径
可用。断点在进入 Goal → Operation 链路的那一步：无 Slurm 站点上 agent
没有动机走 plan/apply——router 0.5.0 的 run Goal 是围绕 Slurm 提交建的，
scheduler=none 时没有可映射的行动路径，技能从"控制面"退化为"site 注册器"。

### 2. env-build 技能 0 调用，构建裸闯

activities 统计：env_build 0 次、raw build 15 次。agent 直接
`ssh m87 'cmake ...'` 反复迭代，期间多次 `rm -rf entity-build` 重建，
并陷入 LD_LIBRARY_PATH / cudart 链接问题的排查（readelf/ldd 调试）。
最终构建成功，但收敛成本全部以裸命令形式支付。

### 3. "恰好运行一次"未做到

transcript 中出现十余份试验 TOML（test_short、test_warm、prod、prod2、
dt、lc、bp_test、proper……），含段错误调试（`ulimit -c unlimited`）。
run root 残留 `proper/`、`neutral_streaming.ckpt` 等中间产物。最终那次
运行本身正确，但过程是"本地试错十几次后跑通"，不是受控的一次执行——
没有 scheduler/控制面约束时，这一任务条款实际上不可强制执行。

### 4. nt2py 是唯一被重度使用的技能

skill 调用分布：nt2py 106、router 18（见上，实为注册）、pgen 2、
env_build 0。`skill_call_share = 0.894` 表面优秀，**但完全由 nt2py 抬高**；
build/run 这两个最需要技能介入的环节恰好全裸。adoption 指标若只报一个
总比率会掩盖这一点——建议报告分环节（build/run/analysis）展示。

## 归因与后续候选（记录，暂不修订）

本轮 S 组结果在任务层面成功，但技能归因上是反面证据：router 的
Goal/Operation 链路在 scheduler=none 站点上没有进入路径。候选改进方向：

1. **router 支持 scheduler=none 的 run Goal**（直接执行 runner：前台/nohup
   运行 + PID/日志收据），让无调度器站点也有 plan/apply 行动路径；
2. **env-build 覆盖"个人主机裸构建"路径**（无 module 系统、无 source-cache
   预置时的依赖收敛），本轮 15 次裸 build 迭代正是它的目标场景；
3. **adoption 报告分环节展示**，避免 nt2py 高频调用稀释 build/run 的
   裸命令信号；
4. task.md 的"恰好一次运行"条款在无 scheduler 站点缺少执行机制，或改写
   为"生产运行与试验运行须可区分（命名/目录隔离）"这类可核验约束。
